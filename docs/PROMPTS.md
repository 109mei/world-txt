# Claude Code 用プロンプト

Sep 25, 2026 · @109mei

**リポジトリ（109mei/world-txt）を開いた Claude Code に、そのまま貼って使う。** P1〜P5 は穴や抜け道を測って見つけるもの（P1〜P3 は見つけたものを直すところまで）、P6〜P9 は直して仕上げるもの。

## 使い方

- **先に、渡すもの一式をリポジトリに置く。** 「修正・改善案」は `docs/IMPROVE.md`、「テーマ・ゲーム性の分析」は `docs/ANALYSIS.md`、このプロンプト集は `docs/PROMPTS.md`、画面設計の24画面（暗い画面12と明るい画面12）は `docs/design/`。Claude Code はこの計画書を直接読めない。プロンプトの「改善案の◯章」は IMPROVE.md、「分析の◯章」は ANALYSIS.md、「画面設計の◯」は docs/design/ を指す
- 1回に1つ貼る。報告を読んでから次を貼る。
- 順番の目安：**P0（読むだけ）→ P1・P2・P3（読み取り）→ P7 段階1 と P17（乱数をなくす）→ P4・P5（今の数字）→ P7 段階2〜5 → P10（読み分け）→ P15・P12・P16（学問の仕組み）→ P13・P14・P11（画面の言葉・情景・現実では）→ P18（開いていく順番）→ P19・P8・P20・P21（演出・見やすさ・明るい画面）→ P22・P23（実績とやりこみ・セーブ）→ P9（見直し）**。不具合が出たらいつでも P6
- 数字の目標は「修正・改善案」の7章。目標と実測がずれたら P4・P5 を回す。
- どのプロンプトも、リポジトリの CLAUDE.md（設計・安全・見た目の決まり）を守る前提で書いている。

## P0 最初に渡す（読むだけ）

渡すもの一式を置いたあと、最初に1度だけ貼る。コードは変えさせず、読んで食い違いを洗い出し、今の数字を残させる。

```text
これから WORLD.txt（題は『ラプラスの庭』にする）を、docs/ に置いた計画書どおりに段階的に直していく。今回は読んで調べるだけで、コードは変えない。

読むもの：
- docs/IMPROVE.md（修正・改善案。「改善案の◯章」はここ）
- docs/ANALYSIS.md（テーマ・ゲーム性の分析。「分析の◯章」はここ）
- docs/PROMPTS.md（このあと1つずつ渡すプロンプト P1〜P23）
- docs/design/（画面設計の試作24画面。暗い画面12と明るい画面12。HTML と PNG。一覧は docs/design/README.md。「画面設計の◯」はここ）
- CLAUDE.md と docs/SPEC.md（今の決まり）

決まったこと（docs/IMPROVE.md の9章）：
- 遊んでいる間は乱数を使わない（ラプラスの決まり）。同じ世界番号と同じ書き換えなら、必ず同じ世界になる
- 学問の仕組み25個はすべて入れ、開いていく順番（分析の13章）で1回に1つずつ紹介する
- 演出に PixiJS を使う（後から読み込み、CSP は変えない）
- 操作とタブは普通の言葉（世界・法則・ノート、書き換える・書き足す・消す）
- 画面は分析の12章「見やすさの点検」どおり。動くのは何か起きたときだけ、絵文字と字の記号は使わない、「何か起きるまで」ボタンは置かない
- 明るい画面も作る。最初は端末の設定に合わせ、メニューで自動・明るい・暗いを選べる（docs/design/ の「明るい画面：」が見本）
- やりこみは腕前と発見の2本（世界ごとの3つの印・世界番号の挑戦・図鑑・改稿者の試練。分析の17章）。連続ログイン・期間限定・くじは入れない
- セーブは今のしくみに、ホーム画面への追加の案内・ファイルでの書き出し・棋譜を足す（分析の18章）

やってほしいこと：
1. 上の資料と src/ を読み、計画書と今のコードが食い違う所（ファイル名・関数名・数字・件数）を一覧にする
2. docs/IMPROVE.md の8章「進め方」の11段階と P1〜P23 の対応を表にし、段階ごとに触るファイルと通すコマンドを書く。docs/WORKPLAN.md に保存する
3. 今の数字を測る：npm test・npm run e2e・npm run sim -- <各ステージ> all 30・npm run ranks・npm run fuzz を回し、結果を docs/BASELINE.md に残す（あとで比べるため）
4. 計画書でわかりにくい所・食い違い・危ない所があれば挙げる。計画書の方を勝手に直さず、報告する

守ること：返事と作業メモはすべて日本語。コミットとプッシュは頼まれたときだけ。今回は src/ を変えない（足してよいのは docs/WORKPLAN.md と docs/BASELINE.md だけ）。
```

## P1 読み取りの穴を総当たりで洗い出す

初めて遊ぶ人が書きそうな文がどれだけ通じるかを測り、穴を塞ぐ。

```text
CLAUDE.md と docs/SPEC.md の 3.3「読み取り」を読んでから始めてください。報告は日本語で。

目的：初めて遊ぶ人が書きそうな自然な文が、どれだけ世界に通じるかを測り、穴を塞ぐ。

1. scripts/corpus.ts を作る。ステージ（food・plague・climate・war・energy・tiny・loop・endless）ごとに、初見の人が書きそうな文を、書き足し用60文以上、行の書き換え用に各行5文以上用意する。言い回し集の例文を写すのは禁止。
   例：「食料が増える」「病気がなくなる」「気温が下がる」「火山は噴火しない」「人は武器を持たない」「石油は減らない」「蔵に食料を蓄える」「作物は干ばつに強い」
2. 各文を、そのステージをはじめて遊べる筆の位（accessFor）で addLine／rewriteLaw に通し、「読めた／意味なし（理由）／止まる（封・重すぎ）／重複」と読み取りの名前を表にする。書き足しと書き換えそれぞれの割合を出す。
3. 意味なしになった文を、原因ごとに分ける：辞書にない言葉／助詞のゆれ（「は」と「が」）／結果を願う文（〜が増える・〜は減らない）／言い回しの規則の不足。
4. 原因ごとに lexicon.json・phrases.json・laws.json の match を直す。コードに言葉を足さない（CLAUDE.md の決まり4）。
5. 直した文を tests/interpret.test.ts に回帰テストとして足す。
6. npm test・npm run fuzz（怪しい読み取り0を保つ）・npm run sim を通し、通じる割合の前後を報告する。目標は書き足し70%以上、行の書き換え90%以上。
```

## P2 逆の読み取りを見つけて直す

```text
目的：書いた文と逆の意味に読まれる文をなくす。今わかっている例：
- 「隕石は大気で燃え尽きる」→「隕石が落ちてくる」
- 「小惑星は地球を避ける」→「隕石が落ちてくる」
- 「植物は水が少なくても育つ」→「植物が光なしで育つ」

1. scripts/polarity.ts を作る。言い回し（phrases.json）と法則の読み取り（laws.json の options）ごとに、例文から「打ち消し」「避ける・それる・防ぐ・燃え尽きる・届かない」「〜が少なくても・〜がなくても」などの言い換えを機械的に作り、読み取りが元と同じ向きか、逆向きか、無関係かを調べる。
2. 向きは、読み取りの係数（mods）の符号と、名前の対（「落ちてくる」と「それる」など）で比べる。逆向き・無関係のものを一覧にする。
3. 上の3例を含め、見つかったものを直す。直すたびに tests/wild.test.ts に足す。
4. npm test・npm run fuzz を通し、見つかった数と直した数を報告する。
```

## P3 画面の呼び名がそのまま読めることを保証する

```text
目的：画面に出る呼び名をそのまま書けば、その意味に読まれるようにする。今は「病気がなくなる」「水が尽きなくなる」「気温が変わらなくなる」「世界がひとつの政府に治められる」など20以上が意味なしになる。

1. tests/names.test.ts を作る。phrases.json の name と laws.json の options の label を、食料危機の世界（書ける範囲の制限なし）に書き足し、その概念・読み取りになることを確かめる。「誰にも確かめられない」「世界の外への命令」など、名前が文になっていないものは、理由つきの除外リストに入れる。
2. 通らないものは match を足して直す（名前を変えるのは最後の手段）。
3. npm test・npm run fuzz を通して報告する。
```

## P4 現象の組み合わせを総当たりする

単語・概念・読み取りの組み合わせで起きることを全部回し、壊れた数値・つまらない必勝法・届かない結末を見つける。

```text
目的：単語・概念・読み取りの組み合わせで起きる現象を総当たりし、壊れた数値・つまらない必勝法・届かない結末を見つける。直す前に報告して止まること。

1. scripts/combos.ts を作る。各ステージで、はじめて遊べる筆の位（accessFor）で書ける読み取りを集める：laws.json の options（消したときの意味も）と phrases.json の例文。
2. 1手を全部回す。次に、1手の上位30の中から2手・3手の組み合わせを総当たりする（書く年は0年目と5年目の2通り）。種は10個ずつ、npm run sim と同じルール本体で回す。
3. 組み合わせごとに、クリア率・平均年数・結末・操作の種類（書き換え／書き足し／削除）・世界容量の最大使用率を scripts/out/combos-<stage>.csv に出す。
4. 次を一覧にして報告する：
   - クリア率55%を超える組み合わせ（とくに1種類の操作だけのもの、消すだけのもの）
   - NaN・無限大・負の人口など、数値が壊れる組み合わせ
   - 意図しない組み合わせで入ってしまう、その場で終わる結末
   - データにあるのに一度も起きない出来事・副作用・結末・組み合わせ（combos.json）
   - 情景が変わらない読み取り（scene の書き忘れ）
5. 直す案を出す。数値は balance.json・laws.json などのデータに置き、コードに書かない（CLAUDE.md の決まり7）。
```

## P5 操作を絞った作戦を測る

「1種類・2種類の操作だけでは勝ちきれない」をテストで守る。

```text
目的：書き換え・書き足し・削除を考えて組み合わせないと勝てないことを、数字で守る（docs/IMPROVE.md の「目標の数字」）。

1. scripts/bots.ts に次のボットを足す：書き換えだけ・書き足しだけ・消すだけ・2種類だけ（各組）・決まった手順（兆しを読まず、決まった年に決まった文を書く）。候補は P4 の上位から自動で選ぶ。書換の力の数と、筆の位の封を守る。
2. 各ステージで種30個ずつ回し、ボットごとの最善のクリア率を表にする。
3. tests/feel.test.ts に目安を足す：書き換えだけ5%以下、書き足しだけ0%、消すだけ0%、2種類だけ15%以下、決まった手順15%以下。今は通らないので it.todo で入れ、今の数字を docs/SPEC.md の5章に書く。
4. 報告は、ステージ×ボットの表と、目安から外れているものの一覧。
```

## P6 不具合を直す（ひな形）

［ ］の中を書き換えて使う。

```text
不具合：［症状。例：食料危機で「人は食べ物を分かち合う」を書くと、翌年に人口が急に1割減る］

1. 同じ種・同じ書き換えで再現する最小の手順を、npm run sim -- <ステージ> <作戦> 1 の年表で作る。再現できなければ条件を変えて探し、それでもできなければそう報告して止まる。
2. 原因をルール本体（src/core）の中で突き止める。どの係数・出来事・副作用が、何年目に、どれだけ効いたかを示す。
3. 直す。数値は src/data に置き、コードに書かない。現実の根拠（なぜ？）が変わるなら、その文も直す。
4. 再現手順を回帰テストにする。
5. npm test・npm run e2e・npm run sim・npm run ranks・npm run fuzz を通す。docs/SPEC.md の数字が変われば直してから、日本語で報告する。コミットは頼まれたときだけ。
```

## P7 改善を段階ごとに実装する

### 段階1 公平さの土台

```text
改善案の段階1「公平さの土台」を実装する。docs/IMPROVE.md の「先に直す修正」を読むこと。

1. 意味のない文では書換の力を使わない。src/core/write.ts の write() で、読み取りが意味なし（noise）のときは commit せず止める（世界容量も使わない）。書き換えシート（src/ui/sheets/EditSheet.tsx）では、入力中に noiseOf で「世界に届かない言葉」とだけ出す。結果の予測は出さない。
2. 書き換えシートに「世界の読み」の帯を足す。入力中の文を言葉に分け、世界が知っている言葉に実線、知らない言葉に点線を引く（unknownWords を使う）。見た目は画面設計の「3 書く」に合わせる。
3. 助詞のゆれ（「病気が消える」と「病気は消える」）を normalize でそろえる。
4. 大きく崩れた年の出来事にも原因の一文を付ける。打撃を強めた要因（農業の縮小など）が書き換えから来ていれば cause を付ける。
5. 「同じ世界でもう一度」（同じ種で開き直す）を足す。まとめて進めるボタンは足さない。何も起きなかった年は、計算の演出を短く（約0.4秒）し、結果の画面を出さずに世界へ戻す（分析の12章）。
6. GameState やセーブの形を変えたら、src/save/migrations.ts と upgradeState も足す（CLAUDE.md の決まり8）。
7. npm test・npm run e2e・npm run screens（画面を目で確かめる）・npm run sim・npm run ranks・npm run fuzz を通し、docs/SPEC.md を直して日本語で報告する。
```

### 段階2 削除を変える

```text
改善案の段階2「削除を変える」を実装する。docs/IMPROVE.md の「3つの操作に役割を持たせる」の削除の節を読むこと。

1. 行を消すと「空白」にする。GameState に空白の行と、空白になった年を持たせる。決まった年数（balance.json に置く。目安3〜5年）のうちに書き換え・書き足しで埋めなければ、世界が「いちばん起こりやすい読み取り」で埋める。laws.json の各行にその読み取り（voidFill）を足し、なぜ？・効き始めの知らせ（onset）・情景の描き方（scene）も書く。例：戦争の行 →「争いは別の形で続く」。
2. 消し跡：消した行の字数の一部（balance.json。目安は半分）を世界容量に残す。
3. 支えている行：laws.json に依存（supports）を足し、支えている行が空白の間は、頼っている行の無理さを足す。
4. 定義のタブで、空白の行に「空白　あと◯年で世界が埋める」を出す（画面設計の「2 WORLD.txt」に合わせる）。
5. P5 の「消すだけ」のボットが、どのステージでも0%になることを確かめる。ならなければ balance.json で詰める。
6. CLAUDE.md の決まり8（セーブの版）と決まり9（onset と scene を書く）を守る。
7. 全部のテストとシミュレーターを通し、docs/SPEC.md を直して報告する。
```

### 段階3〜5（共通のひな形）

```text
改善案の段階［3 3つの役割／4 考える仕組み／5 テーマの軸］を実装する。docs/IMPROVE.md の［該当する章］を読むこと。

- 仕組みを足す前に、P5 のボットで今の数字を測って記録する。
- 仕組みを足したら P4 と P5 を回し、「目標の数字」に入るまでデータ（balance.json など）で詰める。コードに数値を書かない。
- 原因の型を足すときは、最初の3年のうちに見分けられる兆しを必ず2つ以上出す。
- 1回の報告には、変更点・数字の前後・目標に届かないもの・次の案を書く。
- データを3回詰めても目標に動かないときは、仕組みの案に戻って報告し、止まる。
```

## P8 演出（モーションブラー・モーショングラフィックス・VFX）を入れる

```text
画面設計（docs/design/）の「4 計算」「5 因果の連鎖」と、docs/ANALYSIS.md の11章「ラプラスの演出」に沿って、時間を進める演出を入れる。

1. 計算の演出（約1.2秒、タップで飛ばせる）：動くのは2つだけ。年の数字は縦のモーションブラー（SVG の feGaussianBlur、stdDeviation="0 6"）で回る。世界の絵は早回しで、雲・人・影が横のモーションブラーと残像を引いて流れる。数式は止まった薄い文字で置き、読む文（現実では）はこの画面に置かない。何も起きなかった年は約0.4秒にする。
2. 因果の連鎖：書いた一文から、その年に効いた変化へ光の線を順に伸ばす（stroke-dashoffset。1つ約0.3秒、最大6つ）。想定外の変化は線が折れて跳び、着いた所で小さな衝撃波。どの変化をつなぐかは、core が付けている cause から作る（画面の側で新しく推測しない）。
3. VFX：インクのにじみ（書いた瞬間・効き始め）、色収差とゆがみ（世界異常のとき。feDisplacementMap）、彩度を落とす（大崩れのとき）。粒子とゆがみは PixiJS で描く（P19）。1画面で数百個まで。モーションブラーは時間が速く流れている場面だけに使う。
4. 端末の「動きを減らす」設定と、メニューの「情景を動かす」OFF では、ぼかし・粒子・揺れを出さず、線と文字の出方だけにする。画面の外では止める（今の決まりどおり）。
5. Web Animations API で「書いた → 計算 → 連鎖 → 結果」の順番を組み、全体をタップで飛ばせるようにする。
6. 効果音を足す：計算は歯車と紙の音、因果の線は弦の音、想定外は不協和の一音（今の合成の仕組みで作る）。
7. 動きは何か起きたときだけにする（分析の12章「見やすさの点検」）。ずっと続く動きや点滅は作らず、新しく出たものを光らせるのは3回（5秒以内）まで。
8. npm run e2e（CSP に触れないこと）と npm run screens で確かめる。Playwright でスマホ相当の端末の性能に落として、演出中の1秒あたりのコマ数を測って報告する。
```

## P10 書き方の読み分け（性質・制度・条件つき）を入れる

P10〜P23 は、分析のタブの2・5・6・7・11・12・13・17・18章を実装する。先に P7 の段階1（公平さの土台）と P17（乱数をなくす）を済ませておく。

```text
目的：同じ願いでも、書き方で「性質・制度・条件つき」に読み分け、効き方と副作用と組み合わせを変える（分析の5章）。

1. src/data/phrases.json の言い回しに mode（nature・rule・conditional）を足す。まず share（人が分かち合う）と、戦争・犯罪・平等など人の振る舞いの言い回しから。schema.ts（Zod）も直す。
```

## P23 セーブと棋譜

P22 のあとに回す。画面は docs/design/ の Menu（12 メニュー）が見本。

```text
目的：セーブを、docs/ANALYSIS.md の18章に合わせて足す。今の src/save のしくみ（自動保存・控え・読めないセーブを残す・版の変換・persist・別のタブの見張り）はそのまま使う。

1. ホーム画面への追加の案内：最初のクリアのあとに1度だけ出す。ホーム画面から開いているとき（display-mode: standalone）は出さない。出したことはセーブに残す。
2. 書き出し：メニューに「ファイルに保存」（.txt を保存）・「共有」（navigator.share でファイルを送れる端末だけ）・「コピー」を足す。読み込みはファイルからもできるようにする。最後に書き出した日をメニューに出す。新しい筆の位になったあとに1度だけ、書き出しを勧める。
3. 棋譜：世界ごとに、世界番号・ステージ・規則の版と、手の並び（何年目・どの行・消す／書き換える／書き足す・書いた文・読まれ方）を残す。棋譜から世界を作り直す関数を src/core に足す（乱数を使わないので、同じ棋譜なら同じ世界になる）。遊んでいる途中の世界は、今までどおり状態ごとも保存する。
4. 使い道：結末と敗因の振り返りに「再生」（1年ずつ進める）と「分かれ道からやり直す」を足す。やり直した回は、印の「少ない手で」と「早く見抜いた」を付けない。ステージごとに、いちばん良かった棋譜を残す。
5. 規則の版が違う棋譜は再生せず、「今の規則では再生できない」と出す（記録は消さない）。
6. セーブの形を変えるので、版を上げて src/save/migrations.ts に古い版からの変換を足す。セーブの大きさの上限（MAX_SAVE_CHARS）に収まるよう、残す棋譜の数に上限を設ける。

```
